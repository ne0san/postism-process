# 実行基盤とデータ層: イベントソーシングを採用し、AWS Lambda + DynamoDB(イベント) + TiDB(投影)にする

- 状態: 承認
- 決定日: 2026-11-12
- 決定者: オーナー

## 背景

[0004](0004-backend-typescript-effect.md) で、実行基盤とデータベースを未確定のままにしていた。[0001](0001-memo-stored-on-server.md) では、電波がない場所でも書けるように、端末側で溜めて、あとで送る仕組みが必要とされていた。オーナーから、イベントソーシングでオフライン編集を後で反映する構想と、投影はRDBかnewSQLの安いものにする構想が出た。

## 検討した選択肢

- Cloudflare Workers + D1(SQLite)+ Cron Trigger
- Cloudflare Durable Objects(ユーザーごとのオブジェクトにイベントと投影を持つ)
- AWS Lambda + DynamoDB(イベント)+ TiDB(投影)
- AWS Lambda + TiDB(イベントも投影も同じDB)

## 決定

- イベントソーシングを採用する。メモの正本はイベントのログとし、端末はオフラインで発生したイベントを溜めて、あとでサーバーに送る。
- 実行基盤はAWS Lambdaにする。
- イベントの保存先はDynamoDBにする。
- 投影(読み取り用)の保存先はTiDBにする。
- [0004](0004-backend-typescript-effect.md) で未確定としていた実行基盤は、この決定で確定する。言語はTypeScript + Effectのまま。

## 議論での論点

(以下はClaudeの提案を含む)

- 選定理由(オーナー): 経験のある構成であること。公開したときに分かりやすく、合理的であること。Durable Objectsは学習コストが高いと判断した。
- イベントソーシングが向く点(Claudeの提案): 1人用でメモごとに独立しているため競合が起きにくい。分類の履歴が残り、手動の再分類を正解データとして統計に使える。再試行は「分類イベントのないメモ」を引くだけになる。
- 気をつける点(Claudeの指摘): メモの削除とイベントの不変性の扱い。イベントの形を変えるときの対応。イベントの種類は最初に絞る。
- DynamoDBは、ユーザーIDと連番でユーザーごとの順序付きログにでき、条件付き書き込みで連番の衝突を防げる。Streamsから、投影と分類の起動を分けて動かせる(Claudeの提案)。
- 増える負担(Claudeの指摘): Streamsの配信は少なくとも1回のため、投影と分類を冪等にする必要がある。サーバー側の投影は少し遅れる(端末のローカルの投影が先に反映する)。部品が多く、骨組みまでの手間はD1だけの構成より大きい。TiDB Starterにアイドル後の起動待ちがあるかは未確認。
- D1は無料枠で収まり部品も少ないが、オーナーの経験と公開時の見せ方から見送った。Durable Objectsは、ユーザー内の直列化とalarmが自然にできる利点があったが、学習コストから見送った。
- 料金は二次情報を含む(DynamoDB以外は調査時点の値)。採用前に公式で確認する。
- イベントの保存と投影を、差し替えできる境界にする案は、Claudeの提案で、未承認。
