# メモの保存・削除ポリシー: 本文の別保存、旧版7日、即時削除、アカウント削除でイベント全消し

- 状態: 承認
- 決定日: 2026-11-12
- 決定者: オーナー

## 背景

[0024](0024-event-sourcing-and-infrastructure.md) でイベントソーシングを採用したが、イベントは不変のため、メモの削除や編集のときに本文が履歴に残る問題があった。イベントの種類と形を決める前に、保存・削除のポリシーを決める。プライバシーポリシーの記載内容にも関わる。

## 検討した選択肢

- 削除の方式: 本文を別保存(イベントは参照のみ) / イベントごと物理削除 / 暗号化して鍵を捨てる
- 編集前の本文(旧版): 残さない / 内部の保険として期間つきで残す / ユーザーが見られる履歴機能にする
- 旧版の保持期間: 7日 / 30日(主要クラウドサービスのゴミ箱は30日が多い)
- メモ削除: 即時の物理削除 / ゴミ箱(猶予つき)

## 決定

- メモの本文はイベントと別に保存する。イベントは本文への参照だけを持つ。
- 編集前の本文(旧版)は、誤編集の保険として内部だけで持ち、ユーザーには見せない。保持期間は7日で、期間後に自動で削除する(DynamoDBのTTLを想定)。履歴機能をつけるときは期間を見直す。
- メモの削除は、本文の即時の物理削除とする。ゴミ箱は作らない。イベント(削除の事実)は残る。
- アカウントを削除するときは、そのユーザーのイベントも全て消す。
- バックアップは使う。削除後にバックアップに残る期間は、プライバシーポリシーに明記する。
- AIに送る情報は、メモ本文だけにする。位置、画像などの関連データを将来保存することになっても、AIに送るのは本文だけとする。
- サーバーのログには、メモの本文を出さない。出すのは参照(ID、種別)だけにする。
- 完了の取り消し(ワンタッチ)は、将来の機能として「あとでやる」に置く。取り消しは、完了を打ち消すイベントを追加する形で実現でき、本文の旧版は要らない。

## 議論での論点

(以下はClaudeの提案を含む)

- 本文の別保存はClaudeの提案で、オーナーが選択した。暗号化して鍵を捨てる案は、実装の負担が大きいため選ばれなかった。
- 旧版の扱い: Claudeは「残さない」を提案したが、オーナーが「イベントソーシングの意味が薄れる」と指摘し、期間つきで削除する案を出した。イベントソーシングの理由([0024](0024-event-sourcing-and-infrastructure.md)のオフライン同期、分類の履歴、再分類の統計、再試行)は、旧版の本文がなくても成り立つ。
- 保持期間: Claudeは30日を提案したが、強い根拠はなかった。誤編集の保険なら気づくのは早いため、オーナーが7日にした。主要サービス(Google ドライブ、iCloud、OneDrive、Dropbox無料プラン)のゴミ箱は30日だった(Webで確認。今回の旧版は削除後の復元ではなく、性質が違う)。
- 即時削除はClaudeの提案。ゴミ箱は、完了の取り消しとは別の機能として後回しにできる。
- アカウント削除でイベントも全て消すのは、Claudeの提案をオーナーが採用した。オーナーの理由は、ユーザーにとっても安心できること。
- Appleはアプリ内でのアカウント削除を必須としている(Claudeの指摘。公式での確認が前提)。
- 日本の個人情報保護法まわりの確認は、公式の情報が前提。Claudeは法律の専門家ではない。
