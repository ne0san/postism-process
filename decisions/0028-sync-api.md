# 同期APIの形: ID・キーの命名、バッチ送信、イベントの取得、カーソル、本文の添付、複数端末の扱い

- 状態: 承認
- 決定日: 2026-11-16
- 決定者: オーナー

## 背景

[0024](0024-event-sourcing-and-infrastructure.md) でイベントソーシングを採用し、[0026](0026-event-design.md) でイベントとID・冪等性の扱いを決めた。残っていた「同期のAPI」を決める。端末がオフラインで溜めたコマンドの送り方と、サーバーのイベントの受け取り方が中心。

## 検討した選択肢

- 同期前のメモの仮ID: 作成時の冪等キーを仮IDとして使う / 別の仮IDを端末で発行する
- 送り方: 複数コマンドをまとめて順番どおりに送る / 1コマンドずつ送る
- バッチの途中で1件失敗したとき: そこで止める / 失敗した1件だけ飛ばす / 全体をなかったことにする
- 受け取り方: 投影の差分を返す / イベントを返して端末が投影を組み立てる
- カーソル: 連番そのもの / 端末に意味を見せない文字列
- イベントID: ユーザー別連番を使う / 別にUUID v7のIDも持つ
- ページ分割の件数: サーバー固定 / 端末が指定(サーバー側に上限)
- 本文の取り方: 同期レスポンスにサーバーが添付する / 端末が別のAPIで取る

## 決定

- 値の本体はUUID v7。接頭辞で種類を見分ける。
  - `memo_…`: サーバー発行のメモID(0026)
  - `key_…`: 冪等キー。全コマンドに毎回付ける(0026)
  - `local_…`: 同期前のメモの仮ID
- 同期前のメモの仮IDは、作成時の冪等キーを使う。`local_X`は、作成時の`key_X`の本体に`local_`を付けて作る。サーバーは接頭辞を替えて、キーを引ける。同期後、端末は`local_X`と`memo_…`の対応を持つ。
- 場面ごとの必須項目は次のとおり。
  - 端末→サーバーの作成コマンド: `idempotencyKey`必須。`memoId`なし。
  - 端末→サーバーの既存メモへのコマンド: `idempotencyKey`必須。同期済みは`memoId`、未同期は`localMemoId`で指す。
  - サーバーのイベント(`actor`=ユーザー): `idempotencyKey`を保持。`memoId`必須。
  - サーバーのイベント(`actor`=AI/自動): キーなし。`memoId`必須。
- イベントIDは、ユーザー別連番(0024のDynamoDBの順序キー)を使う。別のIDは持たない。
- 端末は、溜めたコマンドを順番どおりに、1リクエストにまとめて送る(バッチ)。
  - 失敗した1件は飛ばして、残りを処理する。
  - 失敗したコマンドと同じメモを対象にする後続コマンドは、「依存失敗」で落とす。別のメモのコマンドは処理する。
  - レスポンスは、コマンドごとに「成功 / 失敗 / 依存失敗」を返す。
- サーバーはイベントを返し、端末が投影を組み立てる。
  - 端末の投影は、UIで見せる項目の部分集合でよい。サーバーの投影(TiDB)は、統計など余計な項目を持てる。
  - 両方に出る項目は、「同じイベント列から同じ状態になる」ことを仕様にする。仕様と、共通のテストデータ(イベント列と期待する状態)で確かめる。
  - 投影ロジックの共有は、クライアントのFWの選定次第とする。
- カーソルは、端末に意味を見せない文字列にする。中身は`{ v, seq }`(`v`は版、`seq`はユーザー別連番)。端末は保存して、次のリクエストにそのまま送るだけにする。
- ページ分割は、サーバーが件数を固定して決める(具体的な件数は実装時に決める)。レスポンスは、イベント、次のカーソル、続きがあるかの印(`hasMore`)。
- 本文は、同期レスポンスにサーバーが添付する(イベント自体は参照のまま)。添付は、そのメモの最新の本文だけにする。ゴミ箱中のメモは添付する。完全削除後は添付せず、完全削除イベントで知らせる。
- 複数端末が同じメモを並行して操作したときは、サーバーの処理順で後勝ちにする(端末側の操作時刻は使わない)。

## 議論での論点

(以下はClaudeの提案を含む)

- 仮IDに冪等キーを使う案は、Claudeが選択肢として示し、オーナーが選んだ。
- オーナーが、IDと冪等キーを区別できる命名にしたいと指摘した。接頭辞を付けることもオーナーが選んだ。値が同じになる件の解決(`key_X`→`local_X`の変換規則)は、Claudeの提案。
- 場面ごとの必須の違いは、オーナーの気づきをClaudeが表に整理した。
- バッチ送信は、Claudeが通信回数の面で有利と提案し、オーナーが選んだ。失敗時の「飛ばす + 依存は落とす」は、オーナーの案。依存の線引きは、Claudeが「同じメモを対象にするか」を提案し、オーナーが、それだけでよいと確認した。
- 投影ロジックの暫定(仕様 + 共通テストデータ)は、Claudeの提案。オーナーが、ロジックが同一である必要性を指摘した。
- 不透明なカーソルは、Claudeの提案。オーナーの質問で、サーバーが中身を読める点と、`v`で連番のリセットにも対応できる点を確認した。
- 複数端末の並行操作は、Claudeが課題を整理し、後勝ちを提案した。オーナーが問題ないと判断し、基準を「サーバーの処理順」と指定した(0026の後勝ちと同じ考え方)。
- イベントIDにユーザー別連番を使う案は、Claudeの提案。
- 本文の添付は、Claudeの提案。当初0025だけを見て「削除済みメモは本文がない」と述べたが、0027でゴミ箱(7日)に置き換わっているため、Claudeが訂正した。
