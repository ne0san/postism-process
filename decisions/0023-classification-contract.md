# 分類の契約: 3種の分類、AIプロバイダー、確信度の扱い

- 状態: 承認
- 決定日: 2026-11-12
- 決定者: オーナー

## 背景

ミニマルの「裏で分類」(#3)の前提として、分類の入出力の契約と、使うAIを決める必要があった([0020](0020-minimal-scope-and-issue-policy.md))。疑問へのAIの回答は、分類とは別の仕組みにするため、ここでは扱わない([0021](0021-resolved-question-display-and-ai-answer-scope.md))。架空のメモ200件(非境界127件、境界73件)で、3社を比較した。

## 検討した選択肢

- 種類: 3種固定 / 追加(アイデア、予定、調べものなど)
- 混在メモ: 1メモ=1種類(A) / 複数に分割(B)
- AI: Claude Haiku 5.5 / Gemini 3.5 Flash-Lite / Jev(分類専用API)
- プロンプト: V1(定義と優先順位のみ) / V2(境界の扱いを明文化)

## 決定

- 種類は ToDo / 疑問 / 記録 の3種固定。追加は、使ってみて「記録」の中身を見てから判断する。
- 1メモ=1種類(A)。分割(B)は「あとでやる」に回す。
- 混在時の優先は ToDo > 疑問 > 記録。迷ったら記録。
- 分類の定義の方針(期待値): 期限・時期・具体的な対象がある「〜したい」はToDo、漠然とした願望は記録。他人の気持ちや理由を問う独り言は疑問。
- 確信度は、ユーザーに見せず、統計として保存する。「低確信度を記録に倒す」使い方はしない(ToDo優先と衝突するため)。
- 暫定のAIは Claude Haiku 5.5、プロンプトは V1。分類は「種類と確信度を返す関数」として切り出し、差し替え可能にする。
- 分類を動かすタイミングは、メモを投げた直後。
- 実装の要件(#3の受け入れ条件の候補): `max_tokens`に余裕を持たせる、タイムアウトとリトライ、失敗時は未分類のまま保留、思考を切る設定の確認。
- プロンプトの追加検証は、問題が出てきたときにやる。

## 議論での論点

(以下はClaudeの提案を含む)

- 3種固定、1メモ=1種類、優先順位、確信度の扱い、検証の進め方は、Claudeの提案をオーナーが承認した。種類を追加する基準は「その種類だけ、扱いが変わるか」(Claudeの提案)。
- 検証結果(全件の正解率。境界73件は期待値のブレが大きいため参考値): V1で Claude 193/200、Gemini 188/200、Jev 187/200。Gemini と Jev は、#173の期待値を疑問に直す前の集計で、直すと Gemini が189、Jev が188。非境界は、Claudeが127/127、Geminiが127/127、Jevが124/127。ToDoの取りこぼしは、Claudeが0件。
- V2(境界の明文化)は、Geminiに効いて(194/200)、Jevには逆効果(184/200)、Claudeには不要だった(191/200)。プロンプトの調整は、モデルごとに効き方が違い、差は期待値のブレと同程度だった。
- 選定理由: ToDoの取りこぼしがない、確信度が統計に使える(正解0.86、不正解0.61)、将来の回答も同じプロバイダーで済む。Geminiは精度は近いが、確信度が張り付いて使えない。Jevは速度とコストに優れるが、大量・高速の分類向けで、このアプリの量と「裏で動く」性質では強みが活きない。
- 3社の単価は検証スクリプトの記録値。採用前に公式で確認する(Jevは非公式値)。
- 疑問へのAIの回答を強みにしたい、というオーナーの意向があり、[0021](0021-resolved-question-display-and-ai-answer-scope.md) で「つける前提」になった。回答は分類と別の仕組みなので、この契約には含めない。回答も同じプロバイダーで出せることが、選定理由の1つ。
- 検証に使ったメモは、すべて架空のもの。このリポジトリには、集計値だけを書く。
- 分類のタイミングを「投げた直後」にするのは、オーナーの指示。投げた直後に1回動かすだけでは、失敗したメモが未分類のまま残るため、再試行の仕組みが別に要る(Claudeの指摘)。
