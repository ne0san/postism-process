# 認証: 公開前提で、Cognito + Apple / Googleサインインにする

- 状態: 承認
- 決定日: 2026-11-16
- 決定者: オーナー

## 背景

[0024](0024-event-sourcing-and-infrastructure.md) の未決事項に認証が残っていた。[0027](0027-trash-and-deletion-revision.md) では、メール台帳の置き場を認証基盤とし、Cognitoを想定していた。オーナーは、最初から公開してサインアップできる前提で作りたいと考えている。

## 検討した選択肢

- 認証基盤: Cognito / Supabase Auth / Firebase Auth / Clerk
- ログイン手段: Apple + Google / Appleのみ / Googleのみ(メール+パスワードは、オーナーが一旦除外)
- トークンの渡し方: Hosted UI(認可コード+PKCE) / ネイティブSDKのトークンを直接交換

## 決定

- 公開してサインアップできる前提で作る(最初の1人用の方式は作らない)。
- 認証基盤はAmazon Cognito(ユーザープール)にする。
- プランはEssentialsを暫定とし、実際に作って確かめる。
- ログイン手段はAppleとGoogleのみ。メール+パスワードは、一旦除外する。
- トークンの渡し方は、Hosted UI(認可コード+PKCE)をシステムブラウザで開く方式にする。アプリ側に「Appleで続ける」「Googleで続ける」のボタンを置き、押したらCognitoの画面を経由せず、直接AppleやGoogleの認証画面に遷移させる。これで、見える画面の見た目は自分で決められる。どのクライアントFWでも同じ方式で使える。
- Appleの「メールを非公開」を使われた場合は、Cognitoが返すアドレスをそのまま台帳([0027](0027-trash-and-deletion-revision.md))に保存する。
- アカウント削除はアプリ内から行えるようにする。順序は、イベント・本文の削除 → 証跡イベント([0027](0027-trash-and-deletion-revision.md)) → Cognitoユーザーの削除(最後。途中で失敗しても再実行できるようにするため)。
- Appleのトークンの失効は、できればやる。できない場合は、Appleの公式の代替手順(データを削除し、ユーザーにAppleの設定から手動で連携を解除するよう案内する)にする。失効できるかの確認は、実装時のタスクにする。

## 議論での論点

(以下はClaudeの提案を含む)

- 認証基盤の候補の洗い出しと、Cognito案は、Claudeの提案。理由は、実行基盤(AWS Lambda)との相性と、0027のメール台帳の想定。他の候補は、無料枠が大きい(Supabase、Firebaseは50,000 MAU)が、構成のベンダーが増える。
- Googleを出すなら、AppleもApp Storeの規約(ガイドライン4.8)の都合で出す必要がある。名指しではないため、自前のメール+パスワードが同等とみなされるかは確認できなかった。オーナーは、Apple + Googleの両方を選んだ。
- アカウント作成を持つアプリは、アプリ内のアカウント削除が必要(ガイドライン5.1.1(v))。Claudeの指摘。
- トークンの渡し方は、ユーザープールのトークンにネイティブSDKのトークンを直接交換する方法を、確認できた範囲では見つけられなかったため、ClaudeがHosted UI方式を提案した。オーナーの指摘(Hosted UIは見た目を変えにくい)を受け、Cognito画面を経由しない直接遷移で解決した。
- 料金は2026-11時点の調査。無料枠は、LiteとEssentialsで10,000 MAU。公式の料金ページでの再確認は未実施。
- Appleのトークン失効が、Cognito経由でできるかは、公式ドキュメントで確認できなかった。
