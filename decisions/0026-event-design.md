# イベントの種類と形、ID・冪等性・コマンドの扱い

- 状態: 承認
- 決定日: 2026-11-15
- 決定者: オーナー

## 背景

[0024](0024-event-sourcing-and-infrastructure.md) でイベントソーシングを採用し、[0025](0025-data-retention-and-deletion-policy.md) で本文を別保存にした。残っていた「イベントの種類と形」を、オーナーが自分で考える形(ハンズオン)で決める。

## 検討した選択肢

- 分類(AI)と再分類(ユーザー): 1つのイベントにまとめる(確信度は任意項目) / 別イベントにする
- 完了(ToDo)と解決(疑問): 別イベント / 1つのイベント
- 作成の再送: 二重に作られてよい / リクエスト日時で同一判定 / クライアントの冪等キー
- 同じ冪等キーで内容が違う再送: 先勝ち(無視またはエラー) / 後勝ち(編集として反映)

## 決定

- 用語を分ける。コマンドは「変更の依頼」で、検証と認可はコマンド側だけで行う。イベントは「通った事実」で、追記のみ。クエリは読み取りで、イベントにしない。
- 全イベントに共通で持たせる項目は、日時、ユーザーID(持ち主)、`actor`(ユーザー / AI / 自動)。
- イベントは次のとおり。
  - メモ作成された(メモID、本文への参照)
  - メモ分類された(AI。メモID、分類、確信度)
  - メモ再分類された(ユーザー。メモID、分類)
  - メモ編集された(メモID、本文への参照)
  - 疑問解決・TODO完了した(メモID。解決と完了は同じイベントで、呼び分けは表示側)
  - 疑問解決・TODO完了が取り消された(メモID)
  - サインアップされた(共通項目のみ)
  - アカウント削除された(共通項目 + メールの鍵付きハッシュ。[0027](0027-trash-and-deletion-revision.md))
- AI分類と人の再分類は別イベントにする。確信度はAI側にだけある。
- 解決状態は、種類とは独立してメモが持つ。記録に再分類しても内部では保持し、戻すと復活する。UIでは記録に出さない。記録に対する「解決する」コマンドは、コマンド側で拒否する。
- 再分類は種類の変更だけを表す。解決の解除が必要な場合は、コマンドが再分類と解決取り消しの2イベントを同時に(atomicに)発行する。
- メモIDはサーバーが発行し、「メモ作成された」に含める。
- 冪等キーはクライアントが毎回発行する。有効範囲は(ユーザー、冪等キー)。同じキーの再送は、内容が同じなら成功扱いでイベントを追加しない。内容が違う場合は後勝ちとして、「メモ編集された」を追加する。
- 既存メモへの操作は、持ち主とアクターの一致をコマンド側で確認する。
- 将来の鍵ローテーションのため、鍵のバージョン欄を、ハッシュと一緒に持たせるかは実装時に決める(今はローテーションしない)。

## 議論での論点

(以下はClaudeの提案を含む)

- 分類と再分類の分離は、オーナーが「確信度の扱いの違い」を理由に選んだ。再分類は、AIの誤りの統計([0023](0023-classification-contract.md))にも使える。
- 解決と完了の統合、解決状態の独立保持は、オーナーの発案。
- メモIDの発行元は、当初Claudeが「クライアント発行」を肯定したが、オーナーの指摘で誤りと分かり、サーバー発行になった。
- 冪等キーは、Claudeが提案した(リクエスト日時で判定する案はオーナー。オフライン作成で時刻がずれる弱点があった)。有効範囲を(ユーザー、キー)にする点はオーナーの指摘。
- 同じキーで内容が違う場合は、Claudeが先勝ちを定番として示したが、オーナーが後勝ちを選んだ(自分のデータだけに影響するため)。
- `actor` という名前はClaudeの提案。
