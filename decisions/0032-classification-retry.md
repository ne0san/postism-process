# 分類の再試行: キュー経由で、エクスポネンシャルバックオフ、3回で諦める

- 状態: 承認
- 決定日: 2026-11-16
- 決定者: オーナー

## 背景

[0023](0023-classification-contract.md) で、分類をメモを投げた直後に動かすことにした。直後の1回だけでは、失敗したメモが未分類のまま残るため、再試行の仕組みが別に要る。0023と [0024](0024-event-sourcing-and-infrastructure.md) の未決事項に残っていた。

## 検討した選択肢

- 再試行のきっかけ: 失敗レスポンスを受けたとき / 定期的な巡回
- 実行の場所: 単一のLambda実行の中 / 再試行だけキュー / 分類を常にキュー経由

## 決定

- 再試行のきっかけは、失敗レスポンスを受けたとき(定期的な巡回は使わない)。
- 再試行は、最初の1回に加えて3回(計4回の試行)。
- 待ち時間はエクスポネンシャルバックオフ。初回の待ちは5秒、倍率は2(5秒、10秒、20秒。待ち時間の合計は35秒)。
- 再試行の対象は、HTTPの500番台、429、408、タイムアウト、ネットワークエラー。それ以外の400番台は、再試行せず、すぐ「諦め」とする。
- 1回あたりのタイムアウトは、プロバイダごとの検証結果で決める。現時点の値は、Claudeが30秒、Jevが10秒。
- 分類は、常にキュー(標準キュー)経由で、メモごとに並列に処理する。再試行も、待ち時間を指定して、キューに戻す。
- 再試行を使い切ったら「分類を諦めた」ことをイベントとして残す(`actor`は自動。メモID付き。[0026](0026-event-design.md) のイベントに追加する)。このイベントも、0029・0030と同じ規則で、コマンド側で検証して二重に発行しない。
- 諦めたメモは、画面の分類アイコンの場所に、赤い丸囲みの「!」を出す。

## 議論での論点

(以下はClaudeの提案を含む)

- 再試行のきっかけ、回数、対象、キュー経由の実行は、すべてオーナーの案。Claudeは、事実(実行時間の計算、Streamsの処理、キューの仕様)を示した。
- 400番台のうち、再試行に意味があるものがあるかは、Claudeが確認した。今回使うAPI(Anthropic)には、408と429以外にはなかった。
- 実行時間の最悪値は、Claudeで155秒(30秒×4+待ち35秒)、Jevで75秒(10秒×4+待ち35秒)。
- Streamsは、同じユーザーのイベントを直列に処理するため、一括投入すると後ろが待たされる。この事実を、Claudeが示した。キュー経由は、これを受けてオーナーが決めた。
- 標準キューは、メッセージごとに待ち時間(最大15分)を指定できる。FIFOキューは、メッセージごとの指定ができないため、標準キューを使う。順序の保証がなく、少なくとも1回の配信になるが、[0029](0029-ai-classify-command-guard.md) と [0030](0030-projection-idempotency-rebuild-auto-events.md) の規則で防げる。
